АЛГОРИТМЫ И РАЗБОР КОДА

1. ПАРАМЕТРЫ

parse_arguments идёт по аргументам слева направо. Имя опции — часть до =.
set_flag узнаёт флаги, set_value выбирает поле Config, read_value получает
значение после = или из следующего аргумента. Множество seen обнаруживает
повторные опции. Затем validate_config проверяет настройки вместе.

Это происходит до HTTP и записи результатов: неверная версия или путь
не должны запускать остальную работу. У выходного файла проверяются
расширение .svg, допустимое имя и существование родительской папки.
Зарезервированные имена Windows, например NUL.svg, не принимаются.
При проверке параметров файл ещё не создаётся.

2. ПОЛУЧЕНИЕ МЕТАДАННЫХ

Для точного корня NpmRepository::exact обращается, например, к
https://registry.npmjs.org/chalk/4.1.2.
Для выбора версии зависимости NpmRepository::resolve получает список
versions по адресу https://registry.npmjs.org/ansi-styles.
Поле dependencies выбранной версии задаёт имена и допустимые диапазоны.
parse_package проверяет соответствие name и version запрошенному пакету.

encode_component кодирует специальные байты URL в %HH. Например, @ и /
в @types/is-number не должны менять структуру пути запроса.
http_get использует WinHTTP: открывает сеанс, подключается к узлу,
создаёт GET-запрос, получает заголовки и читает ответ порциями по 16 КиБ.
HTTPS включает защищённое соединение. Статус не 200 означает ошибку.
Заголовок Accept запрашивает краткий формат метаданных npm.

Таймауты HTTP-операций — 15 секунд; это не общий таймер всего анализа.
Размер одного ответа ограничен 32 МиБ. Метаданные кешируются по имени.
Построитель графа отдельно кеширует выбранный Package по паре
(имя, требование к версии). Кеши существуют только в пределах запуска.
Архивы пакетов анализатор не скачивает.

3. JSON-ПАРСЕР

Parser хранит строку и текущую позицию. parse_value смотрит на первый
значимый символ: { — объект, [ — массив, кавычка — строка,
иначе число, true, false или null.

parse_object читает пары ключ:значение через запятую. Значения снова
разбирает parse_value, поэтому вложенность обрабатывается рекурсивно.
parse_array так же читает последовательность значений.
parse_string понимает кавычки, обратную косую черту и escape-последовательности.
read_unicode превращает \uXXXX в UTF-8, включая суррогатные пары.
parse_primitive проверяет число или узнаёт true, false, null.

Пробелы между элементами пропускаются, BOM UTF-8 в начале допускается.
Повтор ключа, лишняя запятая, незакрытая строка, неверный escape и символы
после корня вызывают ошибку с позицией. Глубина ограничена 128.
as_string, as_array и as_object проверяют тип значения.

Тестовый файл имеет более простой смысл, чем метаданные npm:
{"A":["B","C"],"B":["D"],"C":["D"],"D":[]}
TestRepository проверяет имена и наличие всех упомянутых вершин.
Диапазонов здесь нет: всем пакетам назначается версия из --version.
Размер тестового файла ограничен 4 МиБ.

4. ВЕРСИИ И ДИАПАЗОНЫ

SemVer: major.minor.patch, например 2.4.1. Числа сравниваются по очереди.
Строковое сравнение неверно: 1.10.0 больше 1.9.0.
Предварительная версия 1.0.0-beta.2 меньше стабильной 1.0.0.
Числовые части prerelease сравниваются численно, текстовые — лексикографически;
числовая часть имеет меньший приоритет, чем текстовая. Суффикс после +
не влияет на приоритет. Основные числа хранятся в uint64_t.

parse_version проверяет полную версию. parse_partial_version также понимает
неполные версии и маски. VersionRange превращает диапазон в группы простых
сравнений. Внутри группы действует И, между группами || — ИЛИ.

Примеры для стабильных версий:
4.1.2           ровно 4.1.2
^4.1.0          >=4.1.0 и <5.0.0
^0.2.3          >=0.2.3 и <0.3.0
^0.0.3          >=0.0.3 и <0.0.4
~1.1.4          >=1.1.4 и <1.2.0
2.x             >=2.0.0 и <3.0.0
>=1.0.0 <2.0.0  оба ограничения одновременно
1.0.0 - 2.0.0   обе границы включительно
^1.0.0 || ^3.0.0 подходит одна из групп
*               любая стабильная версия

Для prerelease группа должна явно допускать предварительную версию
с теми же major/minor/patch. Обычный * не выбирает beta автоматически.
Тег latest заменяется значением из dist-tags. Алиас npm:real-name@^1.0.0
направляет запрос к real-name.

select_version перебирает опубликованные версии, отбрасывает неподходящие
и сохраняет наибольшую. Если подходящей нет, сообщается ошибка.
В графе остаётся фактическое имя и точная выбранная версия.

Пример: chalk@4.1.2 требует ansi-styles ^4.1.0. На демонстрации выбирается
ansi-styles@4.3.0. Он требует color-convert ^2.0.1, а color-convert@2.0.1
требует color-name ~1.1.4.

5. РЕКУРСИВНЫЙ BFS

BFS — обход в ширину: сначала корень, потом узлы на расстоянии одного
ребра, потом двух и так далее. visit_level рекурсивно вызывает себя
для следующего уровня целиком. Если бы он сразу вызывал себя для каждого
ребёнка, получился бы обход в глубину DFS.

walk_graph создаёт состояние Search и первый уровень из корня.
visit_level для каждого узла текущего уровня:
1) добавляет его в graph.order;
2) получает соседей через функцию neighbors;
3) записывает все связи в graph.edges;
4) через add_to_level добавляет ещё не посещённых соседей в next.
После всего уровня вызывается visit_level(next, depth + 1).
Пустой уровень завершает рекурсию.

seen помечает узел при добавлении в уровень. Поэтому общий ребёнок двух
родителей не попадает в next дважды, но оба ребра сохраняются.
Цикл тоже остаётся в графе, однако повторного обхода вершины нет.

Разбор A -> B,C; B -> D; C -> D:
Начало: level=[A], seen={A}.
После A: order=[A], next=[B,C], seen={A,B,C}.
После B и C: order=[A,B,C], next=[D], seen={A,B,C,D}.
После D: order=[A,B,C,D], next пуст.
Рёбер четыре: A->B, A->C, B->D, C->D.

В цикле X -> Y -> Z -> X уровни равны [X], [Y], [Z].
При обработке Z узел X уже в seen. Ребро Z->X сохраняется,
но нового уровня с X не возникает.

dependencies читает Package и обрабатывает его словарь dependencies.
Фильтр проверяет имя до запроса, затем фактическое имя после алиаса.
Повторные одинаковые связи удаляются. Если исключён корень, граф пуст
и запроса к реестру не будет.
Пределы: 10000 вершин и глубина до 512 рёбер от корня включительно.
При превышении программа возвращает ошибку.

6. ОБРАТНЫЕ ЗАВИСИМОСТИ

Задача: найти, кто зависит от T, прямо или через цепочку.
Сначала строится обычный граф от --package с учётом фильтра.
find_target ищет T среди его вершин. Отсутствие цели — ошибка;
несколько версий одного имени требуют уточнения имя@версия.

reverse_graph меняет каждое A->B на B->A. Затем запускает тот же
рекурсивный BFS от T. Достигнутые вершины, кроме T, составляют ответ.
Для ромба с целью D уровни [D], [B,C], [A], ответ B, C, A.
Для X->Y->Z->X с целью X ответ Z, Y. Сам X не включается.

Поиск ограничен построенным графом. Он не перечисляет все пакеты
реестра npm, которые где-либо зависят от T.

7. DOT И SVG

print_dot пишет digraph dependencies. Каждый узел выводится отдельно,
чтобы не потерять изолированные пакеты, затем перечисляются рёбра.
dot_label заключает имя в кавычки и экранирует кавычки, обратные косые
черты и переводы строк. Корень выделяется цветом, граф идёт слева направо.

Минимальный смысл DOT:
digraph dependencies {
  "A@1.0.0";
  "B@1.0.0";
  "A@1.0.0" -> "B@1.0.0";
}

save_visualization получает путь SVG и заменяет расширение на .dot
для описания. Создаёт временную папку рядом с результатом, записывает DOT.
render_svg запускает dot.exe -Tsvg через CreateProcessW. Описание идёт
через стандартный ввод, SVG — через стандартный вывод. Файлы заранее
открываются средствами Windows: русские пути и пробелы не приходится
передавать в синтаксисе командной оболочки. Команда не запускается через cmd.

Порядок поиска dot.exe: переменная среды GRAPHVIZ_DOT, путь из CMake,
а если при сборке путь не найден — PATH во время запуска.
GRAPHVIZ_DOT должна содержать путь к EXE без дополнительных аргументов.

Ожидание ограничено 20 секундами. Проверяются код завершения и наличие
тега <svg в результате. При ошибке Graphviz прежние DOT и SVG сохраняются.
После успеха временные файлы переносятся на итоговые пути. Замены двух
файлов последовательны, это не общая транзакция: ошибка файловой системы
между заменами может оставить новую версию только DOT.
TemporaryFiles удаляет временные данные при любом выходе из функции.

SVG — векторный XML-формат: открывается браузером и масштабируется.
Размещение узлов рассчитывает Graphviz, выбор зависимостей — наш код.

8. ASCII-ДЕРЕВО

Граф может содержать общие узлы и циклы. print_ascii отображает его
с отступами обходом в глубину. Это только печать готового графа;
построение по-прежнему использует рекурсивный BFS.

pending — собственный стек элементов TreeLine, а не рекурсивные вызовы C++.
TreeLine хранит имя, отступ, признак последнего ребёнка и событие выхода.
Дети добавляются в обратном порядке, чтобы извлекались в обычном.
|-- означает промежуточную ветвь, `-- последнюю; | сохраняет вертикаль.

active содержит узлы текущего пути. Повтор в active означает цикл:
печатается [cycle], потомки не раскрываются.
seen содержит все уже раскрытые узлы. Повтор вне active получает [seen].
Событие leave убирает узел из active после печати его поддерева.

Общая зависимость:
A@1.0.0
|-- B@1.0.0
|   `-- D@1.0.0
`-- C@1.0.0
    `-- D@1.0.0 [seen]

Цикл:
X@1.0.0
`-- Y@1.0.0
    `-- Z@1.0.0
        `-- X@1.0.0 [cycle]

Связи остаются видимыми, повторное раскрытие не раздувает вывод.
Пустой граф печатается как (empty), изолированный узел — одной строкой.

9. СЛОЖНОСТЬ И ОГРАНИЧЕНИЯ

V — число разных версий пакетов, E — число связей, D — глубина.
Идея BFS требует O(V+E) посещений и O(V+E) памяти графа. В этой реализации
map и set добавляют логарифмическую стоимость поиска; удаление повторных
соседей через std::find может дать O(d^2) для узла со степенью d.
Поэтому нельзя обещать строго O(V+E) для всего приложения.

Дополнительно учитываются сеть, JSON, длины строк и число опубликованных
версий. Выбор перебирает все версии; результат кешируется. Рекурсивный BFS
использует до D+1 вложенных вызовов. ASCII раскрывает каждый узел один раз,
но затраты на отступы зависят от глубины и размера вывода.
Стоимость размещения SVG определяется Graphviz.

Обрабатывается dependencies; devDependencies, peerDependencies,
optionalDependencies как самостоятельные поля не анализируются.
Нет Git-, file- и workspace-зависимостей. Не моделируются package-lock.json,
размещение node_modules, overrides, условия платформы и вся стратегия npm.
При новых публикациях результат выбора диапазонов может измениться.
HTTP и запуск Graphviz в этой реализации рассчитаны на Windows.
