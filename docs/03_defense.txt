ДЕМОНСТРАЦИЯ, ПРОВЕРКИ И ПОДГОТОВКА К ЗАЩИТЕ

1. ПОДГОТОВКА

Открой visual_graph_tool в VS Code, затем Terminal -> New Terminal.
Команды ниже выполняются в PowerShell из корня проекта.
Нужны C++17, CMake, средства сборки Visual Studio и Graphviz.
VS Code — редактор; компилирует код установленный компилятор.

Сборка и все тесты:
powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1 -RunTests

Ожидается: 100% tests passed, 0 tests failed out of 2.
Число 2 означает две группы CTest, а не две отдельные проверки.
Подробный вывод:
.\build\Debug\unit_tests.exe
.\build\Debug\cli_tests.exe .\build\Debug\visual_graph_tool.exe .

Группы содержат 208 модульных и 28 проверок приложения, всего 236.
Модульные тесты подменяют загрузку; интеграционные запускают EXE
и локальный HTTP-сервер. Интернет для них не нужен; dot.exe нужен.

Graphviz: https://graphviz.org/download/
Для новой копии проекта установи Graphviz, добавь его bin в PATH
перед сборкой и перезапусти терминал после изменения PATH.
На этом ноутбуке переносная копия находится в build/tools/graphviz;
CMake находит её автоматически. В Git она не включается.
Если Graphviz перенесён, можно указать фактический путь:
$env:GRAPHVIZ_DOT = 'C:\Program Files\Graphviz\bin\dot.exe'
Отменить переопределение: Remove-Item Env:GRAPHVIZ_DOT

run.bat каждый раз проверяет сборку. Чтобы при демонстрации не видеть
её сообщения, после сборки запускай EXE напрямую, как ниже.

2. ДЕМОНСТРАЦИЯ БЕЗ ИНТЕРНЕТА

Подготовь папку и переменные:
New-Item -ItemType Directory -Force .\build\demo | Out-Null
$app = '.\build\Debug\visual_graph_tool.exe'
$repo = '.\examples\repository.json'

В командах ниже обратная кавычка в конце строки — продолжение PowerShell.
После неё не должно быть пробелов. Можно также объединить строки в одну.

Разветвление с общей зависимостью:
& $app --package A --version 1.0.0 --test-mode --repository $repo `
  --ascii --output .\build\demo\diamond.svg
Ожидается A, ветви B и C, D под обеими ветвями; второй D имеет [seen].
Появятся diamond.svg и diamond.dot. Открой SVG в браузере:
Start-Process .\build\demo\diamond.svg
Get-Content .\build\demo\diamond.dot

Цикл:
& $app --package X --version 1.0.0 --test-mode --repository $repo `
  --ascii --output .\build\demo\cycle.svg
Ожидается X -> Y -> Z -> X [cycle]. В SVG видно замыкающее ребро.

Петля:
& $app --package S --version 1.0.0 --test-mode --repository $repo `
  --ascii --output .\build\demo\loop.svg
Ожидается S и один ребёнок S [cycle]; повторное ребро не появляется.

Изолированный узел:
& $app --package I --version 1.0.0 --test-mode --repository $repo `
  --ascii --output .\build\demo\isolated.svg
Ожидается одна строка I@1.0.0 и одна вершина в SVG.

Фильтр:
& $app --package A --version 1.0.0 --test-mode --repository $repo `
  --filter B --output .\build\demo\filtered.svg
Ожидается nodes=3, edges=2: A -> C -> D. D остаётся достижимой через C.

Обратные зависимости:
& $app --package A --version 1.0.0 --test-mode --repository $repo --reverse D
Ожидается reverse_dependencies=3, затем B@1.0.0, C@1.0.0, A@1.0.0.

Ошибка:
& $app --package A --version bad --test-mode --repository $repo
$LASTEXITCODE
Ожидается сообщение про --version и код 2.

3. ТРИ НАСТОЯЩИХ ПАКЕТА

Эти команды требуют интернета; каждая создаёт DOT и SVG:
& $app --package chalk --version 4.1.2 --ascii --output .\build\demo\chalk.svg
& $app --package ansi-styles --version 4.3.0 --ascii --output .\build\demo\ansi-styles.svg
& $app --package is-number --version 7.0.0 --ascii --output .\build\demo\is-number.svg

Результаты проверки 13.11.2026:
chalk@4.1.2       6 вершин, 5 рёбер — разветвлённый граф.
ansi-styles@4.3.0 3 вершины, 2 ребра — цепочка.
is-number@7.0.0   1 вершина, 0 рёбер — изолированный пакет.

Дерево chalk:
chalk@4.1.2
|-- ansi-styles@4.3.0
|   `-- color-convert@2.0.1
|       `-- color-name@1.1.4
`-- supports-color@7.2.0
    `-- has-flag@4.0.0

Дерево ansi-styles:
ansi-styles@4.3.0
`-- color-convert@2.0.1
    `-- color-name@1.1.4

Дерево is-number: одна строка is-number@7.0.0.
Без --ascii выводятся число вершин, рёбер, порядок BFS и списки соседей.
Для chalk порядок BFS: chalk, ansi-styles, supports-color, color-convert,
has-flag, color-name. Порядок печати дерева отличается от BFS.

4. СРАВНЕНИЕ С npm

Использованы Node.js 24.22.1, npm 10.9.2, Graphviz 14.1.3.
npm нужен только для независимого сравнения, приложение его не вызывает.
Для каждого пакета создан отдельный временный проект. Скрипты пакетов
отключены флагом --ignore-scripts.

Исходные результаты уже лежат в build/demo: chalk-npm.txt,
ansi-styles-npm.txt, is-number-npm.txt, соответствующие -npm.json,
-ascii.txt, -graph.txt и comparison.json. Эти локальные файлы не входят в Git.

Если Node.js и npm доступны в терминале, сравнение chalk можно повторить:
New-Item -ItemType Directory -Force .\build\comparison\chalk | Out-Null
Push-Location .\build\comparison\chalk
npm install chalk@4.1.2 --ignore-scripts --no-audit --no-fund `
  --omit=dev --omit=optional --omit=peer
npm ls --all --unicode=false
npm ls --all --json
Pop-Location

Для остальных повтори в папках ansi-styles и is-number, заменив пакет
на ansi-styles@4.3.0 и is-number@7.0.0. Устанавливать все три в один проект
для этого сравнения не нужно: появится общий внешний корень.
Если npm нет в PATH, подготовленный локальный npm можно вызвать через Node.js:
$npm = (Resolve-Path .\build\tools\npm\package\bin\npm-cli.js).Path
Push-Location .\build\comparison\chalk
node $npm ls --all --unicode=false
Pop-Location

Фактическое сравнение:
Пакет          Наши V/E  npm V/E  Версии и все связи совпали
chalk          6/5      6/5      да
ansi-styles    3/2      3/2      да
is-number      1/0      1/0      да

Сравнивались множества имя@версия и пары рёбер из DOT и npm ls --all --json.
Внешний comparison-* — временный проект, он исключён из сравнения.
Расхождений в данных на этих пакетах нет. Отличается оформление:
npm добавляет служебный корень и символы +--, наш ASCII использует |--,
SVG изображает связи стрелками между прямоугольниками.

В общем случае расхождения возможны. npm ls показывает логическое дерево
установленных пакетов. Наш анализатор выбирает максимальные подходящие
версии по текущим метаданным и объединяет одинаковые имя@версия в один узел.
Старый lock-файл, peer/optional-зависимости, overrides, алиасы и изменения
реестра могут дать другой результат. Совпадение примеров не означает
полной эквивалентности стратегии установки npm.

5. КОРОТКОЕ ВЫСТУПЛЕНИЕ

«Я реализовал анализатор зависимостей npm на C++17. Он получает JSON
из реестра через WinHTTP, выбирает версии и строит граф рекурсивным обходом
в ширину. Вершина — имя вместе с версией. Множество посещённых вершин
предотвращает повторный обход и зацикливание, но рёбра циклов сохраняются.
Есть фильтрация и обратные зависимости через разворот рёбер. Готовый граф
записывается на языке DOT; Graphviz преобразует его в SVG. В терминале
доступно ASCII-дерево. Проверены ошибки параметров и данных, версии,
циклы, общие зависимости и сохранение изображения. Для трёх пакетов
результаты сверены с npm ls: версии и связи совпали».

Затем покажи A, X, --reverse D, chalk и тесты.
В graph.cpp открой visit_level и объясни рекурсию по уровням.
В visualization.cpp покажи print_dot, print_ascii и save_visualization.

6. ВОПРОСЫ И ОТВЕТЫ

Почему BFS рекурсивный, если обычно используют очередь?
Вектор содержит текущий уровень, другой — следующий. Рекурсивный вызов
обрабатывает следующий уровень только после завершения текущего.

Чем BFS отличается от DFS?
BFS идёт по расстоянию от корня, DFS углубляется по одной ветви.
Граф строится BFS; дерево печатается обходом в глубину с собственным стеком.

Почему имя не может быть единственным идентификатором вершины?
Разные зависимости могут требовать разные версии одного пакета.
Объединение по имени потеряет различия и исказит связи.

Почему цикл не вызывает бесконечную рекурсию?
Узел помечается перед добавлением в уровень; повторно туда не попадает.
Само ребро к посещённому узлу всё равно сохраняется.

Почему у D две входящие стрелки, но один узел?
D используется двумя родителями. Пакет общий, отношения разные.

Чем [seen] отличается от [cycle]?
[cycle] — возврат в текущий путь; [seen] — узел раскрывался в другой ветви.
Общая зависимость сама по себе не является циклом.

Что делает --filter?
Исключает имена с подстрокой, не использует регулярные выражения.
Потомок может остаться достижимым через другую ветвь.

Почему выбрана ansi-styles@4.3.0?
Она удовлетворяет ^4.1.0 и является максимальной подходящей на проверке.
Версия 5.x не удовлетворяла бы этому диапазону.

Зачем два кеша?
Один сохраняет весь ответ по имени, другой — выбранный Package по имени
и диапазону. Так меньше сетевых запросов и повторного выбора версии.

Как найти зависимые от D пакеты?
Развернуть рёбра и обойти граф от D, исключив D из ответа.
Ищем внутри исходного графа, а не во всём реестре.

Нарушает ли Graphviz запрет готовых средств получения зависимостей?
Нет: JSON, версии и связи обрабатываются собственным кодом. Graphviz
только рисует готовый граф, а npm отдельно сравнивает результат.
Оба действия предусмотрены пятым этапом задания.

Что будет без интернета?
Работа с реестром сообщит об ошибке. Тестовый режим и автоматические
проверки используют локальные данные.

Что будет без Graphviz?
SVG создать не удастся. --direct и --reverse работают без него.
Обычный --ascii тоже создаёт SVG, поэтому требует Graphviz.

Какие ограничения нужно назвать?
Windows; только dependencies без полной модели npm; нет Git/file/workspace;
лимиты входа и глубины; изменение реестра со временем.
Нельзя обещать поддержку любого package.json и полного поведения npm install.

Зачем тесты CLI, если есть модульные?
Они проверяют передачу аргументов, Unicode-пути, реальный HTTP и процессы,
коды выхода, потоки вывода и появление SVG/DOT на диске.
